# DCAC 升级流程

## 1. 整体流程概述

上位机选择 **DCAC 升级** 后，APP 主控先进入**系统升级态**，并启动系统升级任务。

> **入口文件**：`APP/Application/Sys/sys_queue_task_updata.c`

系统升级任务先拉起 **DCAC 升级任务**，等待 DCAC 任务自身切到升级态；确认后，再打开 **Print 升级通道**，形成如下链路：

```
上位机 <--baiku_proto--> Print <--megmeet_proto--> DCAC
```

---

## 2. 前置握手阶段

DCAC 升级任务启动后，不会立刻进入纯透传，而是先做一段**前置握手**。

> **主逻辑文件**：`APP/Hardware/MD_Dcac/md_dcac_queue_task_updata.c`

### 2.1 探测 DCAC 是否已在 BOOT

| 步骤 | APP 主控动作 | DCAC 模块响应 | 说明 |
|------|-------------|--------------|------|
| 1 | 发送 `F0`，请求升级 | — | 真实语义是**探测 DCAC 当前是否已在 BOOT**，而非开始传文件 |
| 2a | 收到 `F1` | 返回 `F1` | DCAC 已在 BOOT，前置握手结束，进入**透传阶段** |
| 2b | 等待 `F1` 超时 | 无响应 | DCAC 大概率还在**应用态**，继续步骤 3 |

### 2.2 请求 DCAC 跳转到 BOOT

| 步骤 | APP 主控动作 | DCAC 模块响应 | 说明 |
|------|-------------|--------------|------|
| 3 | 发送 `F6`，要求跳转 BOOT | — | — |
| 4a | 收到 `F7` | 无有效载荷 | 跳转指令已确认（F7回复不带有效载荷） |
| 4b | 未收到 `F7` | 无响应 | **不会立刻判失败**，继续重复发送,直到升级任务超时退出" |
| 5 | **固定延时**，等待 DCAC 完成从应用态跳转到 BOOT | — | 500mS |
| 6 | **再次发送 `F0`**，重新请求升级 | — | — |
| 7a | 收到 `F1` | 返回 `F1` | DCAC 成功进入 BOOT，继续执行后续前置握手 |
| 7b | 仍未收到 `F1` | 无响应 | 判定**升级握手失败**，重新开始步骤 3 |

### 2.3 切换波特率（F2 / F3）

| 步骤 | APP 主控动作 | DCAC 模块响应 | 说明 |
|------|-------------|--------------|------|
| 8 | 发送 `F2`，指定目标波特率 | — | 0x00: 9600，0x01: 115200 |
| 9a | 收到 `F3`（成功） | 返回 `F3` | 从机确认切换，APP 主控**同步切换本地串口波特率**（详见 4.1） |
| 9b | 收到 `F3`（失败） | 返回 `F3`（0xFF） | 无对应波特率，判失败 |
| 9c | 未收到 `F3` | 无响应 | 等待超时，判失败 |

### 2.4 上位机传输协议握手与文件头请求（C4 / C2 / C3 / C5）

> **与 BMS 升级对齐**：完成 2.3 后，主控先将 DCAC 设备状态切到升级态，然后主动与上位机完成**传输协议握手**，确认双方进入透传上下文；握手完成后，Print 再进入升级态并转入文件头阶段。

| 步骤 | 方向 | 指令 | 说明 |
|------|------|------|------|
| 10 | APP 主控 → 上位机 | 发送 `C4`（请求传输协议 NAK） | 完成 2.3 后，主控先将 DCAC 切到升级态，再主动向上位机发送 `C4`，请求建立传输通道 |
| 11a | 上位机 → APP 主控 | 回复 `C2`（设置传输协议） | 上位机收到 `C4` 后，下发 `C2`，请求建立传输通道 |
| 11b | APP 主控 → 上位机 | 回复 `C3`（设置传输协议回复） | 主控收到 `C2` 后回复 `C3`，确认传输协议 |
| 11c | 未收到 `C2` | 无响应 | 重复发送 `C4` 三次都无响应，判失败，进入收尾 |
| 12 | — | 固定延时 100 ms | `C3` 回复后，固定等待 100 ms；随后 Print 进入 `DS_UPDATE_MODE`，并立即发送步骤 13 的 `C4` 请求文件头。对上位机来说，这就是收到 `C3` 回复后的第一帧数据请求 |
| 13 | APP 主控 → 上位机 | 发送 `C4`（请求文件头 NAK） | 主控发送 `C4`，请求上位机下发文件头 `C5` |
| 14a | 上位机 → APP 主控 | 回复 `C5`（携带文件头） | 上位机返回 56 字节文件头载荷，供 Print 随后转发为 `A1` |

> **注意**：步骤 10~12 用于建立传输通道；步骤 13~14a 是该通道建立后的首个文件头请求/响应。后续固件包传输不再重复 `C4`/`C2`/`C3` 这一握手。

### 2.5 文件头下发确认（A1 / A2）

> 收到步骤 14a 的文件头 `C5` 后，Print 立即将该载荷转发为 `A1`，并等待 DCAC 返回 `A2` 确认结果。

| 步骤 | 方向 | 指令 | 说明 |
|------|------|------|------|
| 14b | DCAC 模块 → APP 主控 | 返回 `A2`（结果为 0x00） | 文件头校验通过，DCAC 已擦除内部 Flash，**后续进入固件数据透传阶段** |
| 14c | DCAC 模块 → APP 主控 | 返回 `A2`（结果非 0x00） | 文件头校验失败，按错误码处理，进入收尾 |
| 14d | 未收到 `A2` | 无响应 | 等待超时，判失败 |

## 3. 固件数据透传阶段

完成 `C4`/`C2`/`C3` 握手且文件头 `A1`/`A2` 校验通过后，进入固件数据透传阶段。

| 步骤 | 方向 | 指令 | 说明 |
|------|------|------|------|
| 15 | APP 主控 → 上位机 | 发送 `C6`（请求继续发送 ACK）或`C4`（请求重发当前包 NAK） | 透传阶段，2.4 末尾的 `C4/C5` 已经完成文件头这一帧数据交互；在DCAC就收到A2(结果00)后,就要通知Print进入固件数据阶段后，主控通过 `C6` 请求下一包 |
| 16a | 上位机 → APP 主控 | 回复 `C5`（回复数据），携带升级数据包 | 上位机收到 `C4` 或 `C6` 后，回复 `C5`，载荷为升级数据 |
| 16b | 未收到 `C5` | 无响应 | 等待超时，回退发送 `C4` 请求重发当前包 |

> **说明**：
> - `C4` 在当前实现里有三种语义：2.4 前半段用于请求上位机下发 `C2`；2.4 后半段用于请求上位机下发文件头 `C5`；3.x 中用于在超时/校验失败后**请求重新发送当前包**
> - `C6`（请求继续发送 ACK）：用于**请求下一包数据**（当前包接收成功时）
> - 上位机收到 `C4` 或 `C6` 后，均回复 `C5` 携带升级数据包
> - 透传阶段的 `C4`（步骤 15）与前置阶段的 `C4`（步骤 10、13）使用同一命令码，但语义上下文不同：步骤 10 用于建立传输通道，步骤 13 用于请求文件头，步骤 15 不再表示“开始发送”，而是要求重发当前包

### 3.1 指令对接关系

透传阶段涉及 **baiku 协议**（上位机 ? Print）与 **megmeet 协议**（Print ? DCAC）的双向转换，具体指令对应如下：

| 阶段 | 方向 | 上位机（baiku） | Print 侧处理 | DCAC 侧（megmeet） | 说明 |
|------|------|----------------|-------------|-------------------|------|
| **下发数据** | 上位机 → DCAC | `C5`（回复数据，携带升级数据包） | 解析 baiku 帧，提取数据载荷，写入 `tpDcacTask->tReplyBuff` | `A3`（固件包数据），将数据载荷封装为 megmeet 帧发给 DCAC | 下行链路 |
| **本包成功** | DCAC → 上位机 | `C6`（请求继续发送 ACK） | — | `A4` 载荷为 `序号L + 序号H + 状态字`，其中状态字返回 `0x00` | 主控校验 `A4` 包序号与当前帧一致且状态字为 `0x00` 后，组 baiku `C6` 回传上位机，上位机收到后发下一包 `C5` |
| **全部完成** | DCAC → 上位机 | 上位机收到 `C6` 后判断数据已发完，**主动下发 `C7`** | — | `A4` 载荷为 `序号L + 序号H + 状态字`，其中状态字返回 `0x01` | 主控收到状态字 `0x01` 后，需**等待上位机下发 `C7`**，两者都收到后才退出升级 |
| **查询结果** | APP 主控 → DCAC | 无额外 baiku 指令 | 主控根据当前状态机直接触发查询 | `A5`（查询升级结果） | 仅在收到 `C7`/`C8` 或 `A4=0x01` 后触发 |
| **查询回复** | DCAC → APP 主控 | 无额外 baiku 指令 | 仅更新主控本地进度/结果态 | `A6` 返回 `0~100`（进度百分比）或 `0xF7`（当前已是最新版本） | 不通过 `C6` 回传给上位机 |
| **上位机取消** | 上位机 → 主控 | `C8`（回复数据取消发送 CAN） | 主控收到 `C8` 后先触发一次 `A5/A6` 查询当前进度/状态，再进入统一收尾 | — | 上位机主动取消升级 |
| **DCAC 故障** | — | 主控不向上位机回复 | — | `A4` 返回 `0xFD`/`0xFE`/`0xFF`，或 `A6` 返回 `0xF8~0xFF` | DCAC 返回错误时，主控让 DCAC 升级进入**故障状态**，不主动回传上位机 |

### 3.2 数据流向详解

**下行（上位机 → DCAC）：**
1. 上位机通过 **baiku 协议**下发 `C5`（回复数据），载荷为升级数据包
2. Print 任务（`print_queue_task_updata.c`）从 `tpPrintProtoRx->tRxBuff` 读取 baiku 帧
3. 调用 `cBaiku_ProtoCheck()` 解析协议，按当前阶段提取有效载荷并分发
4. 将纯数据写入 `tpDcacTask->tReplyBuff`，通知 **DCAC 升级任务**（`v_dcac_queue_task_updata`）
5. DCAC 任务从缓冲区读取数据，封装为 **megmeet 协议**的 `A3` 帧，通过串口发送给 DCAC 模块

**上行（DCAC → 上位机）：**
1. DCAC 模块回复 `A4`（或 `A6`）等 megmeet 协议帧
2. DCAC 接收任务（`vDcac_RecTask`，`md_dcac_rec_data_proc.c`）解析 megmeet 命令
3. 根据 `A4`/`A6` 的返回值处理：
    - `A4` 载荷固定为 3 字节：`序号L + 序号H + 状态字`
    - `A4` 状态字 = `0x00`（本包成功）→ 主控校验序号后，组 **baiku `C6`** 帧，写入 `tpPrintTask->tReplyBuff`，通知 Print 发送给上位机
     - `A4` 状态字 = `0x01`（全部数据接收完成）→ 主控立即触发一次 `A5`；收到 `A6` 后，仅更新本地进度/结果态。若上位机随后下发 `C7`，主控会再次触发 `A5`，待 `A6 >= 100` 且主机已结束后再进入统一收尾
    - `A6` 返回 `0~100`（进度）或 `0xF7`（当前已是最新版本）→ 仅更新主控本地进度/结果态，不通过 `C6` 回传上位机
    - `A4 = 0xFD/0xFE/0xFF` 或 `A6` 返回 `0xF8~0xFF` → DCAC 升级进入**故障状态**，**不主动回复上位机**
4. 对于正常回复（`C6`），通知 Print 任务，由 `bPrint_SendDataToUsart()` 发送给上位机

> **Print 侧文件**：`APP/Hardware/Print/print_queue_task_updata.c`  
> **DCAC 发送逻辑**：`APP/Hardware/MD_Dcac/md_dcac_queue_task_updata.c`  
> **DCAC 接收与协议转换逻辑**：`APP/Hardware/MD_Dcac/md_dcac_rec_data_proc.c`

| 参数名 | 数值 | 说明 | 代码位置 |

### 3.3 "发一帧，等一回复" 节奏

| 发送帧 | 等待回复 | 说明 |
|--------|---------|------|
| `A3` | `A4` | 逐包发送固件数据，`A4` 载荷为 `序号L + 序号H + 状态字`；收到状态字 `0x00` 后主控组 `C6` 回传，上位机收到后发下一包 `C5` |
| `A5` | `A6` | 查询升级结果，`A6` 仅用于主控内部更新进度/结束态；其中 `0xF7` 表示当前已是最新版本，`0xF8~0xFF` 为错误码 |

- 当前帧对应的回复还没回来时，APP 主控**不会继续放下一帧**
- 等待超时 → **重复发送当前帧**，避免中途数据帧受干扰导致下位机未收到
- **升级过程中不做周期性 `A5` 轮询**，仅在收到 `C7`、`C8`、`A4=0x01`，或当前包 `A4=0x00` 且上位机已结束时才触发 `A5` 查询

### 3.4 方向总结

| 方向 | megmeet 帧 | baiku 帧（对应上位机侧） |
|------|-----------|------------------------|
| 上位机 **主动发送** | — | `C2`、`C5`、`C7`、`C8` |
| APP 主控 **主动发送** | `F0`、`F6`、`F2`、`A1`、`A3`、`A5` | `C3`、`C4`、`C6`（回复上位机） |
| DCAC 模块 **回复** | `F1`、`F7`、`F3`、`A2`、`A4`、`A6` | —（其中仅 `A4=0x00` 会被主控转换为 `C6` 请求下一帧） |

## 3.5 数据校验环节

主控收到上位机下发的 `C5` 数据包后，在转发给 DCAC 之前，需进行以下校验：

| 校验项 | 说明 | 失败处理 |
|--------|------|---------|
| 包序号核对 | 核对 `C5` 载荷中的包序号是否与预期一致 | 包序号不一致 → 发送 `C4` 请求重发当前包 |
| CRC 校验 | 对 `C5` 载荷中的固件数据进行 CRC 校验 | CRC 失败 → 发送 `C4` 请求重发当前包 |
| 帧长度校验 | 核对数据包长度是否符合协议要求（192/224 字节，最后一包除外） | 长度异常 → 发送 `C4` 请求重发 |

> **注意**：校验失败时，主控**不会**将错误数据下发给 DCAC，而是直接通过 `C4` 请求上位机重新下发当前包。

## 3.6 超时重试与失败重传机制

升级过程中存在两条独立的通信链路，各自有独立的超时重试机制。

### 3.6.1 上行链路超时（主控 ? 上位机）

| 场景 | 触发条件 | 处理动作 | 最大重试次数 |
|------|---------|---------|------------|
| `C4` 无回复（握手阶段） | 发送 `C4`（步骤 10）后未收到 `C2` | 重复发送 `C4` | 3 次 |
| `C4` 无回复 | 发送 `C4` 后未收到 `C5` | 重复发送 `C4` | 3 次 |
| `C6` 无回复 | 发送 `C6` 后未收到上位机 `C5` 或 `C7` | **发送 `C4` 请求重发当前包** | 3 次 |

> **关键区别**：发送 `C6` 后未收到回复，**不能**继续发 `C6`，而应回退到发送 `C4`，通知上位机重新下发当前数据包。

### 3.6.2 下行链路超时（主控 ? DCAC）

| 场景 | 触发条件 | 处理动作 | 最大重试次数 |
|------|---------|---------|------------|
| `A3` 无回复 | 发送 `A3` 后未收到 `A4` | **重复发送当前 `A3` 帧** | 3 次 |
| `A5` 无回复 | 发送 `A5` 后未收到 `A6` | 重复发送 `A5` | 3 次 |

> **注意**：下行链路超时重发的是**同一帧数据**，不会增加包序号。

### 3.6.3 超时重试流程示例

```
主控发送 C6（请求下一包）
    ↓
等待上位机回复 C5/C7
    ↓
超时 ──────────────────────→ 重试计数 +1
    ↓                              ↓
收到 C5 ──→ 校验通过 ──→ 封装 A3 ──→ 发送给 DCAC
    ↓           ↓              ↓
校验失败      超时           收到 A4=0x00
    ↓           ↓              ↓
发送 C4    重发 A3          发送 C6（请求下一包）
（请求重发）   ↓              ↓
              重试超限         收到 A4=0x01
                  ↓              ↓
              判失败          触发 A5，等待 A6
                                            ↓
                                    仅更新本地进度；收到 C7 后再次 A5/A6
                                            ↓
                                    A6>=100 且已收到 C7
                                            ↓
                                        进入统一收尾
```

## 3.7 传输完成确认

传输完成的触发与确认逻辑如下：

1. **上位机判断数据发完**：上位机收到主控的 `C6` 后，检查当前是否还有未发送的固件数据
   - 还有数据 → 继续下发 `C5`
   - 数据已发完 → **主动下发 `C7`**（传输完成）

2. **主控收到 `C7` 后的处理**：
   - `C7`**不需要**透传给 DCAC
   - 主控需**继续等待 DCAC 回复 `A4=0x01`**（整体固件接收完成并校验通过）
   - **两者都满足**（收到 `C7` 且 `A4=0x01`）后，才允许进入统一收尾

3. **超时处理**：若收到 `C7` 后长时间未收到 `A4=0x01`，按通信超时处理，判失败。

## 4. 特殊处理

### 4.1 F2 / F3 波特率切换

`F2` 和 `F3` 的波特率切换**不是纯透传处理**。

- **DCAC 升级发送任务**在 Step 8 根据 `tUpdata.ulBaud` 主动发送 `F2`
- 等 DCAC 真正回了成功的 `F3`，APP 才在**本地切换 DCAC 串口波特率**

> **文件**：`APP/Hardware/MD_Dcac/md_dcac_rec_data_proc.c`

### 4.2 A4 响应处理

| A4 状态字 | 处理逻辑 |
|------------|---------|
| **本包成功** | `A4` 载荷中的包序号校验通过且状态字为 `0x00` 时，主控继续发下一包 |
| **全部完成** | `A4` 状态字为 `0x01` 只表示 DCAC 已收完固件数据；当前代码会立即触发 `A5/A6` 查询，查询结果只用于更新主控本地进度/结果态。若随后收到 `C7`，会再次查询，待最终进度满足完成条件后再统一收尾 |

> **说明**：`A4` 的完整载荷为 `序号L + 序号H + 状态字`，其中状态字 `0xFD/0xFE/0xFF` 表示故障。

> **文件**：`APP/Hardware/MD_Dcac/md_dcac_rec_data_proc.c`、`APP/Hardware/Print/print_queue_task_updata.c`

## 5. 异常处理分支

### 5.1 文件头校验失败（A2 返回非 0x00）

| A2 返回码 | 错误含义 | 处理动作 |
|----------|---------|---------|
| `0xF7` | 当前已是最新版本 | 记录日志，进入收尾 |
| `0xF8` | 内部读写错误（Flash 读写错误） | 记录日志，进入收尾 |
| `0xF9` | 固件大小错误 | 记录日志，进入收尾 |
| `0xFA` | 软件版本号错误 | 记录日志，进入收尾 |
| `0xFB` | 硬件版本 3 错误 | 记录日志，进入收尾 |
| `0xFC` | 硬件版本 2 错误 | 记录日志，进入收尾 |
| `0xFD` | 硬件版本 1 错误 | 记录日志，进入收尾 |
| `0xFE` | 地区代码错误 | 记录日志，进入收尾 |
| `0xFF` | 项目名错误 | 记录日志，进入收尾 |

> **注意**：A2 返回非 0x00 后，DCAC 不会擦除内部 Flash，5 秒内未收到新的升级固件信息（或其他指令），DCAC 会自动跳回 APP。

### 5.2 固件包传输错误（A4 返回错误码）

| A4 状态字 | 错误含义 | 处理动作 |
|----------|---------|---------|
| `0xFD` | Flash 读写错误 | DCAC 侧 Flash 异常，记录日志，进入收尾，需重新升级 |
| `0xFE` | 没有收到过 A1 命令 | 文件头丢失，记录日志，进入收尾，需重新升级 |
| `0xFF` | 数据接收完成，校验出错（升级文件 CRC32 错误或固件 CRC32 错误） | 整体校验不通过，记录日志，进入收尾，**需重新升级** |

> **重升级流程**：A4 返回 `0xFD/0xFE/0xFF` 时，主控记录错误码并进入收尾。上位机需重新发起完整的升级流程（从 F0 探测开始）。

### 5.3 DCAC 故障状态

当 DCAC 返回以下错误时，主控让 DCAC 升级进入**故障状态**：
- `A4` 返回 `0xFD/0xFE/0xFF`
- `A6` 返回 `0xF8~0xFF`（查询结果错误码）

**故障状态行为**：
- 主控**不主动向上位机回复**任何帧
- 等待上位机下发 `C8` 取消命令或总超时触发收尾
- 最终由统一收尾函数处理

### 5.4 上位机主动取消（C8）

| 场景 | 处理流程 |
|------|---------|
| 上位机下发 `C8` | Print 任务识别 `C8`（`baikuCMD_REPLY_CANEL`） |
| 主控动作 | 先将主机结果置为取消态，再触发 `A5` 查询 DCAC 当前进度/状态；若 `A6` 返回 `0~99`，则继续轮询直到完成或取消超时 |
| DCAC 侧 | **不需要**显式通知 DCAC 取消，统一收尾后直接结束 DCAC 升级任务 |
| 波特率恢复 | 串口恢复到 `9600` |
| 状态恢复 | 系统和 DCAC 设备状态恢复到工作态 |

> **注意**：当前实现中，C8 取消不会透传给 DCAC，也不会发送特定“取消升级”指令；主控会先补发 `A5/A6` 查询当前进度/状态，若 `A6` 返回 `0~99` 则继续轮询，随后按取消结果进入统一收尾。DCAC 端依赖自身的超时机制跳回 APP（若仍停留在 BOOT）。

## 6. 进度查询机制（A5 / A6）

### 6.1 查询触发时机

`A5/A6` 查询升级结果**仅在以下边界条件下触发**，升级过程中不做主动轮询：

| 场景 | 触发方 | 说明 |
|------|--------|------|
| **收到 `A4=0x01` 后** | 主控 | DCAC 返回整体固件接收完成（`A4=0x01`）后，主控立即发送一次 `A5`，并用 `A6` 结果更新本地进度/结果态 |
| **收到 `C7` 后** | 上位机 | 上位机下发传输完成命令 `C7` 后，主控再次发送 `A5`；当后续 `A6 >= 100` 且 `cDcac_GetUpdataResult > 0` 时，完成收尾条件成立 |
| **收到 `C8` 后** | 上位机 | 上位机下发取消命令 `C8` 后，主控发送 `A5` 查询 DCAC 当前进度/状态；收到 `A6` 或查询超时重试结束后，按取消结果进入统一收尾 |

> **注意**：
> - 升级过程中**不做周期性轮询** `A5/A6`，仅在上述边界条件下开始查询；若已进入查询阶段且 `A6 < 100`，则继续轮询直到完成或超时。
> - `A6` 返回 `0~100` 表示升级校验进度（十进制），返回 `0xF7` 表示当前已是最新版本；返回后 DCAC 会在 100ms 内跳转 APP。

### 6.2 查询流程

```
收到 A4=0x01，或上位机发送 C7/C8
    ↓
主控识别为查询请求，下发 A5 给 DCAC
    ↓
DCAC 回复 A6（进度、`0xF7` 最新版本或错误码）
    ↓
主控仅更新本地进度/结果态
    ↓
若 A6 返回 `0~99`，则继续发起 `A5/A6` 轮询，直到返回 `100`、`0xF7` 或取消超时收尾
    ↓
若该次查询由 `C8` 触发，则按取消结果进入统一收尾
```

## 7. 失败 / 退出条件汇总

升级过程中，以下情况都会触发**失败或退出收尾**：

- [x] 发送失败（串口发送缓冲区满或硬件故障）
- [x] 等待回复超时（F1/F3/A2/A4/A6 等，超时 1000ms）
- [x] 回复内容异常（A2/A4/A6 返回错误码）
- [x] 上位机主动发退出命令（`C8`）
- [x] 系统空闲超时（长时间无数据交互）
- [x] 总超时（整个升级流程超过最大允许时间）
- [x] 数据校验失败（包序号、CRC、帧长度错误）
- [x] DCAC 故障（Flash 读写错误、校验错误等）

## 8. 统一收尾

所有**成功、失败、超时、主动退出**，最终都走**统一收尾函数**。

> **文件**：`APP/Application/Sys/sys_queue_task_updata.c`

### 收尾动作

1. 清空升级缓冲（`tpDcacTask->tReplyBuff`、`tPrintTxBuff` 等）
2. 把 DCAC 串口恢复到 `9600`
3. 结束 **Print / DCAC / SYS** 三个升级任务
4. 把系统和 DCAC 设备状态恢复到**工作态**
5. 记录最终升级结果（成功/失败/错误码）
6. DCAC 端依赖自身超时机制跳回 APP（若仍在 BOOT）

### 收尾触发条件

| 触发源 | 触发条件 | 说明 |
|--------|---------|------|
| 正常完成 | 已收到 `C7`，且此前已进入 `A4=0x01` 完成边界，后续 `A5/A6` 查询返回进度 `>= 100` | 升级成功 |
| 上位机取消 | 收到 `C8` | 主动取消 |
| 握手失败 | F0/F1、F2/F3、A1/A2 超时或错误 | 前置阶段失败 |
| 传失败 | A3/A4 超时或 A4 返回错误码 | 数据传输阶段失败 |
| 总超时 | 超过最大升级时间 | 安全保护 |
